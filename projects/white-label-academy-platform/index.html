Platform engineering

White-label Academy Platform

A reusable Flutter platform powering eight published, branded academy apps.

Reference app: Golden Academy (opens in a new tab)
Role
Designed and built the platform: architecture, the core package, the template app and the content-protection layer.
Platform
Flutter · iOS & Android

Problem

Every new academy application used to start by copying an existing codebase. Fixes and feature updates then had to be repeated by hand across every separate app.

Solution

I designed and built a reusable core package, tech_app_core, together with a template application. A new academy app is now a typed configuration over a shared foundation instead of a fork of another app.

Architecture

How the shared platform, the configuration contracts and the branded apps connect.

Engineering decisions

Configuration as a typed contract

Branding, tenant identity and enabled features are expressed through AppTenantConfig, AppColorScheme and AppFeatureFlags. Branded apps provide values; the core owns behaviour, so apps cannot diverge in logic.

Feature flags decide the product

Capabilities such as payments, parent monitoring, QR attendance and exams are switched per tenant, so one codebase ships different products without branching.

One networking layer, tenant-aware

A shared Dio client with tenant-aware authentication means every app reaches its backend through the same path.

Cubit-based state, reusable routing

Features are Cubit-driven modules with shared routing and UI components, keeping screens consistent across apps.

Security that fails closed

Protected content is only shown when protection is confirmed. If the platform refuses protection, the content stays hidden instead of falling back to an unprotected display.

Content protection

Paid learning content must not leak. The protection layer is built to fail closed.

  1. 01

    A protected screen opens

    It acquires a protection token. Tokens are reference-counted, so replacing or stacking screens never leaves an unprotected gap, and the last release switches protection off.

  2. 02

    Protection is applied

    Android: FLAG_SECURE. iOS: a secure capture layer, plus detection of active recording or mirroring. Work runs through a single serialized queue and is re-asserted on lifecycle and configuration changes.

  3. 03

    The gate decides

    Content renders only when protection is confirmed. Failed, pending or unsupported states keep it hidden. The gate fails closed and never falls back to an unprotected display.

Device integrity checks

  • Root / jailbreak
  • Emulator
  • Developer mode
  • ADB

Developer-mode and ADB checks run through a native Kotlin method channel.

Main features

Platform capabilities

  • Configurable feature flags
  • Multiple payment methods
  • Purchases from a whole package down to a single lecture
  • Video playback from direct/R2 and YouTube sources
  • PDF viewer
  • Exams and results
  • QR attendance
  • Parent monitoring

Operations

  • Firebase messaging
  • Crashlytics and performance monitoring
  • Offline handling
  • Forced update system

Technology

  • Dart
  • Dio

Outcome

Eight published applications run on the same reusable foundation, so a fix or feature is written once and reaches every app.
